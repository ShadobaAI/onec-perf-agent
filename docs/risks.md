# Риски и ограничения проекта

Документ фиксирует технические гипотезы и риски `onec-perf-agent`. Оценки предварительные; способы интеграции и качество диагностики необходимо подтвердить экспериментально.

## Основные риски

| Риск | Приоритет | Проблема | Подход |
| --- | --- | --- | --- |
| Корреляция теста, кода 1С и SQL | Критический | У источников нет единого сквозного идентификатора операции; параллельные тесты, фоновые задания и повторяющиеся запросы затрудняют атрибуцию | Начать с изолированного последовательного теста; исследовать идентификаторы сеансов/соединений, контекст операций и временные метки; фиксировать степень достоверности связи |
| Достоверность выводов ИИ | Критический | Дорогой оператор плана, запрос в цикле или медленный метод ещё не доказывают неоптимальность | Разделять подтверждённые проблемы, вероятные гипотезы и статические предупреждения; прикладывать доказательства |
| Привязка SQL к исходному BSL | Высокий | Платформа преобразует запросы 1С в SQL, в том числе в несколько команд; текстовое сопоставление ненадёжно | Использовать контекст технологического журнала и связь с запросом 1С; не обещать точную привязку там, где её нет |
| Автоматизация замера через `dbgs.exe` | Высокий | `dbgs.exe` — сервер отладки, не готовый API сбора метрик; программное управление замером требует проверки | Отдельный PoC; на первом этапе допускать импорт экспортированных результатов замера |
| Накладные расходы диагностики | Высокий | Подробные журналы, планы и профилирование меняют нагрузку и времена отклика | Разделить нагрузочный прогон с лёгким мониторингом и диагностический прогон с детальной трассировкой |
| Воспроизводимость | Высокий | Результаты зависят от объёма данных, кэша, статистики SQL, конкурирующей нагрузки и инфраструктуры | Фиксировать окружение и состояние данных, прогревать систему, выполнять повторы и сравнивать с baseline |
| Ограничения тестовых фреймворков | Средний | YAxUnit и Vanessa исполняют сценарии, но сами по себе не гарантируют реалистичную параллельную нагрузку | В MVP использовать их как исполнителей операций; отдельно исследовать управление интенсивностью, параллелизмом и изоляцией данных |
| Объём и конфиденциальность данных для LLM | Средний | Журналы и исходники могут быть объёмными и содержать чувствительные данные | Агрегировать и отбирать данные до LLM, ограничивать контекст, обезличивать сведения, контролировать передачу внешним моделям |

## Важные ограничения источников

- **MS SQL Query Store** хранит статистику по планам и интервалам агрегации, а не готовую трассу конкретного теста. Сохранённые планы в Query Store — оценочные; при необходимости фактических планов нужен отдельный способ получения.
- **Замер производительности 1С** работает в контексте отладки и может влиять на измерение. Его данные следует использовать для диагностики кода, а не как единственный источник нагрузочных показателей.
- **Технологический журнал 1С** даёт важный контекст SQL-вызовов, но подробный сбор данных требуется ограничивать по длительности и событиям.
- **Исходники конфигурации** должны соответствовать версии, на которой выполнялся тест; иначе привязка к строкам может быть неверной.

## Первый исследовательский эксперимент (PoC)

**Цель:** проверить, можно ли воспроизводимо построить связь `Тест → Метод/строка BSL → Запрос 1С → SQL-запрос → Метрики`.

1. Создать YAxUnit-тест, который вызывает известный метод 1С с запросом к MS SQL Server.
2. Выполнить тест в изолированной базе, зафиксировать `run_id`, версию конфигурации, временной интервал и окружение.
3. Собрать технологический журнал и SQL-метрики; дополнительно получить замер производительности доступным способом.
4. Реализовать детерминированный парсер и корреляцию без участия LLM.
5. Проверить количество вызовов, длительность и корректность привязки к исходнику.
6. Повторить эксперимент с двумя параллельными тестами и выявить ошибочные либо неоднозначные связи.

**Критерий успеха:** для контролируемых сценариев все подтверждённые связи можно проверить по исходным данным; неоднозначные события явно помечаются и не выдаются за точные. Численные пороги покрытия и допустимой погрешности определить после первого прогона.

## Решение по этапам

1. **Корреляция и воспроизводимые измерения** — технический фундамент.
2. **Детерминированная диагностика и отчёт** — поиск дорогих операций, запросов и блокировок.
3. **LLM-анализ** — объяснение причин и рекомендации на основе отобранных доказательств.
4. **Расширенное нагрузочное тестирование** — параллельные исполнители, управление нагрузкой и анализ деградации.

Не начинать с автономного ИИ-оркестратора, пока не проверена достоверность корреляции.
